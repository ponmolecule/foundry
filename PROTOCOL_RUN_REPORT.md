## r101 verification addendum — source-share vs natural-period flow semantics

## r116 verification addendum — lagged managed-securities targets + funding-waterfall ownership

r116 corrects two managed-securities integration defects discovered against the source-model securities roll-forward. First, managed portfolios now own an explicit target-source timing contract: **Current period** or **Prior period**. Prior-period timing also owns an explicit first-model-period initialization, **Zero** or **Opening source**, so the engine never silently substitutes opening equity/deposits for a model whose first projected securities balance is intentionally zero. New managed portfolios default to `prior_period` + `zero`; r114/r115 saved portfolios that lack these fields retain their historical `current_period` semantics for backward compatibility.

The motivating source-model chronology is now a first-principles regression: M1 managed securities are zero, M2 securities are established from M1 Equity × the authored target ratio, M3 from M2 Equity, and so on. Current-period targeting remains supported and continues to participate in the existing fixed-point solve when selected. Prior-period targeting consumes the already-finalized preceding balance-sheet Series value and therefore does not introduce a same-period Equity → securities → income/AOCI → Equity loop. FIW exposes target timing and prior-period initialization when explicitly authored, Calculation Audit exposes the resolved target-source value, and the narrow Securities & AOCI UI exposes both controls without instrument-specific branching.

## r117 verification addendum — accrual accounting for self-timed tiered/banded assessments

r117 separates **expense recognition** from **cash settlement** for the generic self-timed `piecewise_linked` / tiered-banded Opex primitive. Existing saved components remain backward-compatible: if no component-level recognition contract is present, the historical behavior continues to recognize the full calculated amount at the cash event. New or edited components may instead select **Accrue evenly over cadence interval** and explicitly author the first covered model period. The event cadence and first event remain the cash-settlement contract. No regulator name, calendar month, band schedule, or engagement-specific coefficient is hard-coded into the runtime grammar.

For spread recognition, Foundry calculates one assessment for each cadence interval from the configured observed base, divides that assessment evenly across the covered engine periods for Income Statement expense, and settles the full assessment at the configured cash event. Each linked component independently accumulates `cash − expense`: negative balances post to **Accrued operating expenses** before payment; positive balances post to **Prepaid operating expenses** after payment; the timing balance clears at the end of the coverage interval. This timing bridge is additive to the existing static Opex timing balances and the legacy simplified-OCC shortcut without netting unrelated component balances against one another.

Validation fails closed when the assessment base would not yet be knowable at the first covered period. In a January-start monthly OCC-style setup, the source-faithful authoring is Semiannual cadence, first cash event M3, spread recognition beginning M1, and a three-month observation lag: M3 therefore uses the opening/Dec-31 measurement base for the Jan-Jun assessment, while M9 uses M6/Jun-30 for Jul-Dec. The same primitive remains calendar-agnostic through ordinal periods, so non-January model starts and non-OCC tiered assessments use the identical grammar. The Calculation Audit now distinguishes recognized expense from event cash and surfaces the assessment/coverage diagnostics. FIW capability mapping also records the tiered-component recognition mode.
