# r389 — save revisions and compact expense authoring

Built on r388. No financial engine equation or stored monetary-unit migration.

- Successful saves take their application revision from the JSON response, rather than depending solely on the transport ETag. Named reads use an application revision header, with strong/weak ETag fallback. Repeated saves continue with the newly issued revision. A simulated proxy stripping save response revision headers reproduces the old missing-head failure and passes with this change. This is a confirmed failure path, not proof of the exact production intermediary behavior. Missing-revision, changed-revision and deleted-record conflicts have distinct messages; stale writes remain refused. No force overwrite, revision rebasing or automatic recovery adoption.
- Expense Formula bases are compact expandable rows, with sign, source, measure and annual rate summarized together. The combined base and subsequent factors have distinct sections. Expansion survives re-rendering for the same item. Newly enabled bases use a neutral numeric multiplier of 1; existing authored factors are retained.
- Products' validation banner refreshes in place after previews, without replacing inputs. Responses from superseded assumptions are discarded even during debounce. Fee-stream errors identify product and stream names instead of array offsets. The confirmed stale banner could show an empty multiplier error after the loaded schedule was already calculating successfully.
- Deposit entered/weighted amounts per customer display and accept $000s through the existing money-Series conversion, including their path editors and calculated summaries. Internal amounts stay in dollars. Previously entered amounts render divided by 1,000; users must not divide/re-enter them. Per-account and per-unit fee costs remain raw dollar prices, with explicit labels and explanatory text.

Validation: 15 backend cases pass across save safety, existing reusable formulas and deposit-rate schedules. Browser tests against the actual isolated FastAPI server cover repeated saves with stripped headers, two-tab stale refusal, recovery-copy isolation and reload. Authoring browser checks cover $000s round-trip, compact base editing, banner clearing without input replacement, existing fixed/float schedules and overrides, and containment at 1440/1024/768. Inline JavaScript syntax and git diff checks pass. No production engagement data accessed. Customer-flow versus linked-Series menu unification remains deferred.

Before deployment, download the current unsaved workspace JSON. After deployment use a fresh tab and open the intended saved version. Do not discard an unsaved tab until the current work is verified saved. An already unverified tab cannot acquire overwrite permission merely by installing a new release.
